# Offline semantic search benchmark

## Reproduce

From the repository root, run the benchmark tests and print the actual summary:

```sh
OFFLINE_TESTS_REQUIRE_OS_ISOLATION=1 bash scripts/run_offline_tests.sh -p test_semantic_benchmark.py
```

Run the complete offline regression suite:

```sh
OFFLINE_TESTS_REQUIRE_OS_ISOLATION=1 bash scripts/run_offline_tests.sh
```

For the complete JSON report, including all questions, gold labels, authorized
sources, returned source IDs, scores, and per-query metrics:

```sh
PYTHONPATH=tests:. .venv/bin/python -B -m scripts.benchmark_semantic_search
```

The last command uses the existing Python startup network guard. The first two
also require verified OS network isolation. No application server, Gemini,
BigQuery, cloud SDK, backup, credential, model, or external index is needed.
Only standard-library modules and the existing retriever are used. The harness
temporarily supplies a retrieval-flag-only configuration module, restores the
original module afterward, and never changes runtime settings or allowlists.

## Fixed inputs and scope

- Benchmark version: `synthetic-questions-v1`.
- Corpus version: `synthetic-business-v1`; existing scoring, synonyms, threshold,
  and top-three limit are unchanged.
- Exactly 40 unique questions: 20 English and 20 Arabic.
- Categories: 14 synonyms, 10 paraphrases, 4 ambiguous, 6 unsupported, and
  6 authorization-boundary questions.
- Gold labels and per-question synthetic allowlists are fixed in
  [the benchmark](../scripts/benchmark_semantic_search.py), not generated by a
  model or inferred from retrieval results.
- Fixture/corpus SHA-256:
  `1b77be29289797ef9fc1a335cc83e63bbf3397ee701c020eb703468c1dc5dc01`.

Each question runs enabled and disabled in two scenarios:

1. **Multi-source simulation:** the seven synthetic corpus source IDs are
   eligible unless a question explicitly restricts them. This is a benchmark
   allowlist, **not** actual production authorization or a grant of access.
2. **Single approved source:** intersect each fixture allowlist with
   `nsp_ai_synthetic.synthetic_athletes`. No other source becomes eligible.

Both modes exercise `build_semantic_context`. Disabled mode must not call the
retriever and returns no hints. This is an abstain-all retrieval baseline,
**not** a benchmark of the application's existing model-based router. No
inference or SQL execution occurs. Runtime guards and disabled PERSONAL_GCP
settings are untouched.

## Metric definitions

Relevance is source-level business-topic relevance, not proof that a schema
can answer a query. Gold relevance is intersected with each effective allowlist.
Ambiguous questions have two relevant sources; either is a relevant first hit,
but Recall@3 requires both. Retrieving a match does not settle clarification.

- **Precision@1:** mean of 1 when the first returned source is relevant,
  otherwise 0, over queries with at least one authorized relevant source.
  Empty results score 0.
- **Recall@3:** mean fraction of authorized relevant sources returned in the
  first three positions, over the same positive queries.
- **MRR:** mean reciprocal rank of the first relevant source in the returned
  top-three list, or 0 if absent. This is truncated MRR because retrieval
  returns at most three matches.
- **Out-of-scope rejection:** fraction returning no hints among questions with
  no authorized relevant source. This includes unsupported requests and
  authorization exclusions; it is retrieval abstention, not an API rejection.
- **Unsupported-request rejection:** the same measure on the six intrinsically
  unsupported questions only, reported separately to avoid conflating scope
  understanding with authorization filtering.
- **Unauthorized-source leakage:** fraction of all 40 queries returning any
  source outside that query's effective allowlist. Absolute unauthorized
  match counts are also reported. This query-level rate has a defined zero
  denominator-free interpretation even when disabled mode returns no matches.

The report also includes per-language ranking and out-of-scope metrics.
Precision@1, Recall@3, and MRR are **N/A (`null`) for the single-source
scenario**: they cannot establish ranking discrimination with only one
approved source. Retrieval detection/abstention and authorization remain
meaningful. Single-source positive/negative counts are 4/36; multi-source
counts are 28/12.

| Multi-source simulation | Disabled | 0.000 | 0.000 | 0.000 | 12/12 (100%) | 6/6 (100%) | 0/40 (0%) |
| Single approved source | Enabled | N/A | N/A | N/A | 28/36 (77.78%) | 4/6 (66.67%) | 0/40 (0%) |

English and Arabic have identical aggregate metrics in this fixture. Enabled
multi-source retrieval returns 65 matches; enabled single-source retrieval
returns 12. All four runs return zero unauthorized matches.

Validation on 2026-10-24: **8 benchmark tests passed; all 384 offline regression
tests passed**, including the disabled PERSONAL_GCP semantic subprocess.
Both commands verified macOS OS-level TCP/DNS isolation and the Python startup
network guard before collection. Diagnostics, syntax, and whitespace checks
passed. The full suite emitted an existing Starlette deprecation warning and
simulated error-path logs, but no test failures.

### Interpretation and limitations

The positive questions intentionally exercise the hand-authored vocabulary;
perfect ranking on 28 small synthetic positive cases is **not** evidence of
general Arabic/English understanding, real-world routing accuracy, or improved
SQL generation. There is no held-out client dataset or statistical confidence
claim. The version/hash make changes to this fixture visible.

The out-of-scope weaknesses are deliberately retained in the benchmark:
prediction requests containing sports terms and deletion requests containing
license terms retrieve hints despite being unsupported. Pure TF-IDF does not
understand those intents. In the single-source scenario, generic athlete/sport
terms can also retrieve the sole synthetic source for questions whose gold
source is not authorized. That is a relevance false positive, **not**
unauthorized-source leakage.

Disabled mode's 100% abstention is trivial and loses all positive retrieval;
it is not a better router. Existing source authorization, capability checks,
clarifications, read-only SQL guardrails, and profile restrictions must remain
authoritative. This benchmark does not bypass or replace them.
